# 多叉车 NLP 死锁优化恢复项目——完整上下文

**1. 项目仓库与背景：** 主仓库为 https://github.com/Counter-Attack-Mankind/fork_planner ，参考仓库为 https://github.com/Counter-Attack-Mankind/LIOM 。项目采用 ROS1 Noetic、C++ 和 RViz，现有系统已经包含多叉车离线路径生成、滚动协调、TTC 预测避碰、A1 资源协调、优先级分配和固定 Retreat 死锁恢复机制。请先审查主仓库的实际代码和上下游调用关系，不要仅凭本文描述推断实现细节。

**2. 核心研究目标：** 在不破坏原有正常协调策略的前提下，引入独立的非线性轨迹优化方法解决多叉车死锁。当常规固定 Retreat 无法解除双车死锁，或者确认三车及以上的等待环时，进入优化恢复流程，通过 CasADi + IPOPT 联合优化参与车辆的局部恢复轨迹，完成无碰撞脱困，最终重新接入原始路径并继续原有任务。

**3. 总体设计原则：** NLP 只作为常规协调失效后的兜底机制，不替代原来的 TTC、A1 协调和优先级系统。整个功能尽量集中在独立 ROS 功能包 `forklift_nlp_recovery` 中，原规划器仅负责状态发布、死锁触发、冻结、轨迹执行交接和恢复协调。避免大规模重构原有系统。

**4. 当前死锁检测机制：** 主仓库的 `DeadlockManager` 已经具备基于车辆 STOP 状态和 `blocker_id` 等待依赖关系的闭环检测能力，可以识别双车及三车以上的等待环。双车优先执行原有固定 Retreat 恢复；当退让失败、没有足够退让空间或达到次数上限时，进入 `NLP_PREP`。三车及以上的已确认等待环可以直接进入 `NLP_PREP`。具体状态转移、超时阈值和条件必须阅读当前源代码确认。

**5. 当前 NLP 恢复状态与冻结机制：** 已新增 `NLP_PREP` 恢复阶段，并使用动态车辆 ID 数组保存死锁参与集合，而非写死两辆车。仿真规划节点已经具有进入 `NLP_PREP` 后冻结运动计划的逻辑。后续需要在此基础上实现优化求解、轨迹执行和恢复协调；不能把当前的冻结功能理解为完整的 NLP 接管，也不能默认实车具有相同的安全冻结能力。

**6. 当前恢复数据接口：** 主规划器通过 `/forklift_planner/recovery_snapshot` 发布只读恢复快照，包含车辆真实 ID、当前位姿有效性、当前路径、`path_s`、`path_gen`、速度、运行状态以及恢复阶段、参与车辆集合等信息。具体消息结构位于 `experiment/sandbox_msgs/msg/`。未来优化器应该直接复用这个数据接口，避免另建一套相互矛盾的车辆状态来源。

**7. 当前独立功能包：** 已建立 `forklift_nlp_recovery`，主要包含 `corridor_builder.h/.cpp`、`recovery_visualizer_node.cpp`、`config/recovery.yaml`、独立 launch 和 RViz 配置。当前主要完成了恢复快照读取、几何走廊构造、候选终点提取和可视化；CasADi 联合优化、轨迹求解及执行闭环尚未完成。实际完成程度应以最新仓库代码、编译和运行测试为准。

**8. Debug 与 Auto 模式：** `recovery.yaml` 支持 `debug` 和 `auto`。Debug 模式使用 YAML 指定的真实车辆 ID 集合，对这些车辆持续构造和显示 AABB。Auto 模式在正常运行时只显示普通橙色车辆，不主动构造优化走廊；进入 `NLP_PREP` 后，根据恢复事务自动选取所有参与车辆，锁定当时的位姿、路径、候选终点及 AABB 并在 RViz 显示。未来求解器应使用与可视化一致的冻结输入。

**9. 优化参与车辆：** NLP 必须从一开始采用通用 N 车架构，不写死双车或三车。死锁参与集合由 `nlp_vehicle_ids` 确定。每辆参与车辆具有独立的优化状态、控制变量、起终点和安全走廊，所有车辆在统一时间轴上进行联合求解。新增车辆时应通过数组和循环自动扩展，而不是复制多份双车约束代码。

**10. 优化起点：** 每辆车的 NLP 起点采用进入恢复状态时锁定的当前实际后轴位姿，不能直接使用原路径上最近的理想点来替代。仿真采用仿真车辆状态，实车采用经过有效性检查的真实定位状态。初始速度、航向、前轮转向等边值需要结合实际控制状态和现有运动学模型确定，不能自行假定所有测量值都为零。

**11. 优化终点：** 每辆车的终点从原始离线路径中选择安全重接入点，包含后轴位置、航向、路径弧长和路径实例信息，并要求恢复结束时车辆能够安全停车或满足明确的状态交接条件。目前第一阶段主要按照当前路径弧长向前搜索候选终点，遇到障碍允许按规则提前截短；该终点只是几何候选点，尚未保证多车联合优化一定可行。后续需要检查终点组合能否真正解除死锁。

**12. 车辆运动学：** NLP 继续使用以后轴中心为参考点的自行车运动学模型，统一处理前进、倒车、速度、加速度、转向角和转向角速度约束。后轴坐标是运动学状态、原始路径及起终点的统一参考，不能因为采用车身中心碰撞模型就改变原规划器、定位或控制器的坐标定义。数学模型、参数和控制边界应从仓库及 LIOM 参考实现中核对。

**13. 车辆碰撞模型：** 当前方案明确采用单圆盘近似，而非双圆盘。圆盘位于车辆几何中心，后轴至几何中心的偏移由实际车辆参数计算。优化变量依然是后轴状态，只有几何约束需要转换到圆盘中心。圆盘半径通过 `recovery.yaml` 配置；缺省或无效时由车辆真实尺寸计算。RViz 同时显示实际矩形车身和圆盘，用于观察近似误差。

**14. AABB 的作用：** AABB 是为简化静态仓库环境避障而生成的安全走廊。其目的是把复杂的货架碰撞约束转化为对车辆圆盘中心的简单盒约束，使 CasADi + IPOPT 无须对每个优化节点反复计算车身与全部货架的复杂几何碰撞。AABB 不是车辆间动态避碰的替代品；车辆间避碰仍需单独建模。

**15. AABB 的当前生成算法：** 从锁定的实际车辆起点出发，沿原始离线路径向前截取一段候选恢复路径，将沿途采样的后轴位姿转换为车身圆盘中心，生成 AABB 种子。每个种子按上、下、左、右方向逐步扩张，直到碰到货架、地图边界或者尺寸限制。相邻矩形需要保证连通，必要时插入中间种子；最后删除包含关系中的冗余矩形，并合并可以安全合并的矩形。因此最终可能只有一个 AABB，也可能出现两个或多个矩形组成 T 形、L 形走廊。

**16. AABB 几何参数：** 当前仓库允许分别配置圆盘半径、货架膨胀扣减、地图边界内缩扣减、AABB 扩张步长、路径种子采样步长、候选终点距离、矩形最大宽高以及连通补点深度。所有数值必须从当前 `forklift_nlp_recovery/config/recovery.yaml` 和相关地图配置读取，不要在新代码或提示词中另写一套固定参数。几何合法性与 RViz 显示必须保持一致。

**17. 多个 AABB 的 NLP 使用方式：** 对于 T 形或者 L 形的多个连通矩形，优化器不能直接把其整体外包矩形作为自由空间，否则可能允许车辆穿越货架。需要确定不同轨迹节点所属的 AABB，合理设计相邻矩形之间的切换与交叠区域，并避免跨矩形切换时穿过非法空间。第一版可以采用预先分配节点所属矩形的方式，不必立即引入混合整数优化。

**18. 初始解生成思想：** 下一步新建独立的 NLP 初始解生成函数，以锁定的现场位姿、原始离线路径、候选终点和各车 AABB 为输入，沿原路径插值生成每辆车的初始轨迹。所有参与车辆使用统一时间轴，同时初始化速度、转向及控制变量。初始解允许暂时违反部分车辆间动态避碰约束，由 IPOPT 联合优化修正；但要正确处理初始实际位姿偏离原路径、前进倒车换向、航向连续性、变量边界和时间初始化。

**19. 初始解的后续改进：** 不要求第一版初始化算法就能完全消除多车死锁。若直接将多辆车的原路径插值放在相同时刻导致 IPOPT 收敛困难，可在后续引入等待段、车辆先后通行顺序或时间错位初始化。优先先实现简单、可复现的初始解，再根据真实求解结果增加必要改进，避免提前设计复杂启发式规则。

**20. NLP 建模方式：** 推荐采用 C++ CasADi 建模并调用 IPOPT，直接在独立功能包中组织通用 N 车 NLP。若明确选择 AMPL + IPOPT 才需要使用 `.mod` 文件。应先检查主仓库与 LIOM 的已有依赖及数学模型，再确定文件组织、离散方法、状态与控制变量、时间参数化和 IPOPT 求解选项，不要将 AMPL 和 CasADi 的接口混用。

**21. 静态环境避障约束：** 对每辆参与优化的车辆，把优化状态转换为车身圆盘中心，再将其约束在当前所属 AABB 内部。静态货架已经在 AABB 构造阶段处理，NLP 内原则上不再逐个添加全部货架的碰撞约束。必须确保实际使用的 AABB 与 `CorridorBuilder` 的输出一致，且不能在多个矩形之间产生几何穿越。

**22. 参与优化车辆间的动态避碰：** 所有 NLP 车辆在同一时间轴上联合优化，对任意两辆不同的参与车辆自动加入圆盘中心距离约束。相同半径车辆要求圆心距离不小于两个半径之和，半径不同则使用各自半径之和。约束在所有必要时间节点生效，并额外进行节点之间的连续碰撞检查。不得仅依赖优先级或初始路径顺序代替联合避碰。

**23. 非参与优化车辆的静态避碰：** 场上其他车辆不作为 NLP 决策变量，在恢复期间应保持静止。其中只有可能与参与车辆 AABB 走廊发生空间冲突的车辆才需要加入静态圆盘避碰约束。筛选条件不能简单地判断静态车圆心是否位于某个 AABB 内，而应考虑其圆盘半径与 AABB 的最短距离。对整个走廊都足够远的车辆可以直接排除，以控制优化规模。

**24. 静态车辆的冻结前提：** 上一条把非参与车辆当作静态障碍物的前提，是规划器确实能够在整个 NLP 求解和轨迹执行期间保证它们保持停止。仿真模式已有全局冻结基础，但正式执行时需要区分允许恢复车辆运动和其余车辆冻结。实车模式则必须具有独立可靠的停止确认与安全保护，不允许只在数学模型里假设其他车辆静止。

**25. NLP 优化目标：** 以尽快完成死锁恢复为主要目标，同时合理抑制控制输入及其变化，使轨迹能够被现有控制器跟踪。具体目标函数、权重、变量维度、离散积分公式和求解参数不应凭空设定，应结合仓库的车辆模型、速度限制、参考 LIOM 以及现有控制器能力共同确定。

**26. IPOPT 求解后的验证：** 求解器返回成功不等于轨迹可直接执行。必须验证运动学残差、边值、变量上下界、AABB 约束、参与车辆间碰撞、附近静态车碰撞，以及离散节点之间的连续轨迹安全。还要通过真实矩形车身进行独立碰撞检查，尤其在圆盘半径或货架膨胀经过扣减时，不能将简化圆盘的可行性误认为真实车辆绝对安全。

**27. 轨迹执行：** 优化成功并通过验证后，把 N 车联合 NLP 输出转换为每辆车可执行的时间化轨迹。仿真中需要新增独立的恢复执行阶段，允许参与优化的车辆按优化轨迹推进，同时保持其余车辆冻结；实车中需要检查轨迹消息格式、现有控制器输入、速度方向、前进倒车换向和跟踪能力。不能在原有全局冻结仍禁止运动推进的情况下直接发送轨迹就认为能够执行。

**28. 轨迹执行期间的安全控制：** 所有参与车辆需要协调一致地执行优化轨迹，并持续监测当前位姿、跟踪误差、时序偏差和碰撞风险。某辆车出现明显跟踪失败、定位无效或异常停车时，其他车辆不能继续盲目按照原定时空轨迹推进。需要具有统一暂停或安全停止机制，但第一阶段不应超前实现复杂的实车故障恢复策略。

**29. 恢复结束与解除冻结：** 只有参与优化的车辆全部完成有效的恢复动作，并确认到达各自指定的重接入位置、航向及允许的速度条件后，才能更新原始路径进度及恢复事务。清理旧运动计划、重建常规预测并确保首次滚动协调安全，然后解除其他车辆冻结，恢复 TTC、A1 和任务执行。不能在 IPOPT 返回成功、轨迹刚发布或单车提前完成时直接解除冻结。

**30. 阶段一——几何与可视化：** 已实现独立功能包、恢复快照、等待环参与车辆读取、Debug/Auto、单圆盘中心转换、AABB 生成、候选终点和 RViz 可视化。当前代码已具备 `NLP_PREP` 事务锁定和仿真冻结逻辑。该阶段主要完成代码开发，正式完成度仍应由最新编译结果与运行验证确认。

**31. 阶段二——优化输入和初始解：** 这是接下来优先实施的阶段。首先将已锁定的现场状态和 AABB 组织成统一的 N 车优化输入数据结构，再编写独立的原路径插值初始解函数，验证每辆车起终点、节点数量、时间轴、AABB 分配和速度方向的正确性。暂时不改变车辆运动控制。

**32. 阶段三——通用 N 车 NLP 求解：** 引入 CasADi + IPOPT，构造运动学、边值、控制限制、AABB、参与车辆两两动态避碰以及附近静态车辆避碰约束。先独立运行优化、记录求解状态和约束残差，并在 RViz 中显示最终优化轨迹。算法从架构上直接支持 N 辆车，但验证应从双车、三车逐步扩展至更多车辆。

**33. 阶段四——仿真闭环：** 将 NLP 与现有 `NLP_PREP` 死锁恢复状态机连接，完成冻结快照、求解、验证、轨迹执行、原路径重接入和恢复常规协调的完整链路。重点测试固定 Retreat 失败、无法后退、多车等待环、NLP 求解失败及恢复执行异常等场景。

**34. 阶段五——实车验证：** 在仿真闭环稳定后接入实车，包括动捕状态读取、真实车辆停止确认、优化轨迹下发、控制器跟踪、执行监控、物理碰撞校验及恢复任务。实车安全控制必须独立验证，不能简单复用仿真运动推进机制。

**35. 开发与沟通要求：** 任何修改之前，请先遍历项目的相关文件及其上下游调用，明确现有实现，不能只检查预先猜测的几个文件。优先保持最小修改和独立模块边界，不修改正常 TTC、A1、优先级、任务分配或原始路径生成机制。发现具体问题再修复，不增加无依据的复杂补强。每次只完成当前开发阶段，提供明确的修改位置、修改内容、编译测试结果和仍未解决的问题。

**36. 当前任务定位：** 现在不是重新设计死锁检测器，也不是重新实现 AABB，而是利用现有 `NLP_PREP`、冻结快照及安全走廊，开始构造真正的 N 车联合优化器。下一步优先完成优化输入组织、原始路径插值初始解、各时间节点 AABB 分配，再实现 CasADi + IPOPT 求解，之后才是轨迹执行和全局解冻。

**最终目标：** 让两辆、三辆乃至更多叉车在原有协调无法解除死锁时，能够通过统一的联合 NLP 计算出符合运动学、静态环境避障及多车时空避碰约束的局部恢复轨迹，并在安全执行完成后重新接入原路径，恢复整个仓库系统的正常运行。
